# SDD Multi-Agent Kit — Milestone 2 Spec

**Document:** `spec_milestone_2.md`
**Milestone:** 2 of 5
**Status:** Draft

## Cumulative History

Inherited from M1 (see M1 docs + PHRs milestone_0/000-003, milestone_1/001-003): the kit is an npm-distributed SDD framework for CLI coding agents; the seven-article constitution is fixed; the critic panel is locked (seven models, three provider keys, one free tier) per ADR-001/ADR-003 — the *shipped* config carries seven, but the mechanism is config-driven and accepts more; the retry policy (unparseable → ≤1 retry, i.e. up to 2 attempts; transport/timeout/429 → ≤5 tries with adaptive backoff; no cross-round exclusion — a failed critic participates again next round) is fixed; the kit's core process content — master skill, constitution template, providers.yaml, and ten sub-skills — is delivered and verified under `kit/`. M1 explicitly deferred the critique engine's *automation* (the `critique-loop` sub-skill and the orchestration/validation scripts) to M2. This milestone delivers that automation.

## Goal

Deliver the critique engine that M1's master skill points to: the `critique-loop` sub-skill plus two Python scripts (`kit/scripts/orchestrate_critique_loop.py`, `kit/scripts/validate_critique.py`) that together run the real two-pass, seven-model critique loop against a milestone document — one document per invocation (Pass 2 over the five-doc set is run as five invocations) — reading the panel from M1's `providers.yaml`, enforcing the critique response schema, absorbing transport/invalid-critic failures per the retry policy, and logging critique JSON to `outputs/critique-log/`. This is the component that makes "models checking models" real rather than a described invariant.

## User Scenarios

**US-1 — Run Pass 1 on a document.** An agent has drafted `spec_milestone_N.md` and invokes the critique loop for Pass 1. It gets back a critique-log JSON with each valid critic's rubric scores and issues, with `needs_clarify`-tagged issues separated, ready for Clarify. Pass 1 stops when every objective issue is resolved and the full `needs_clarify` list is compiled (the Pass-1 rule line instructs the critics; the agent enforces the stopping rule).

**US-2 — Run Pass 2 on the five-document set.** After Clarify, the agent runs the loop with full rigor (Pass 2 scores both objective and subjective dimensions — all five) across all five docs, and the agent re-checks Clarify consistency during adjudication (the re-check is the agent's, not the critics' — critics never see Clarify answers). It stops only when every currently-valid critic scores perfect — "currently-valid" means the round's own valid critics; a critic absent from a round (transport/invalid) neither blocks nor satisfies the condition, it simply participates next round — (perfect = `overall_score` 10 — a 10-with-zero-issues is valid and also perfect; only a sub-10 score with zero issues is invalid) or the round cap is hit, escalating to the human.

**US-3 — Flaky critic.** A provider 429s or a critic returns invalid JSON. The loop retries per policy and logs the failed critic for the round; the critic participates again next round — no critic is ever excluded across rounds — and the run never silently dies or stops.

**US-4 — Add a model via config.** A maintainer adds a model to `providers.yaml` (M1 config). The loop picks it up with zero code change, because it reads the panel from config, not from hard-coded lists.

## Functional Requirements

**FR-1 — `kit/scripts/orchestrate_critique_loop.py`.** CLI script (one invocation = one pass over one document). CLI: `--doc <path> --name <id> --pass 1|2 [--round N] [--out <dir>] [--round-cap N] [--timeout S] [--config <path>]` (round default 1, positive integer; out default `outputs/critique-log/`; round-cap default 25, `0` disables; timeout default 600; config default `kit/config/providers.yaml`). It: reads the panel from `kit/config/providers.yaml` (structure per `spec_milestone_1` §4.3 — `providers[].models`, ordered `critic_slots`); loads the document to critique; builds the critique prompt (embeds the PLAN.md §4.3 rubric schema — held in the script as a constant, synchronized with PLAN.md by the maintainer; the script does not read PLAN.md at runtime — and the document text; the **Pass-1 vs Pass-2 rule line differs** — Pass 1 instructs critics to score only the objective dimensions of the schema — clarity, completeness, edge_case_coverage, internal_consistency, all checkable against the document alone; testability is subjective (it needs a runtime) and out of Pass-1 scope — the schema still requires the key, so Pass-1 critics emit `testability: 0` (0 = not assessed in this pass) — and to tag genuine business/subjective decisions `needs_clarify`; Pass 2 is full rigor (scores all five dimensions) and re-checks Clarify consistency — the re-check is performed by the agent during adjudication (the sub-skill's triage step, which has the Clarify answers); the script's prompt embeds the document and the schema only, so it has no cross-document state — the Pass-2 rule line therefore does not mention Clarify (critics never see Clarify answers; the `needs_clarify` category is pass-independent — Pass-2 critics may still tag genuinely new business/subjective decisions with it); the pass rule line is a single configurable sentence in the script's prompt-template constant — the rubric dimensions themselves come from the schema, so the "which dimensions" enumeration lives with the schema, not duplicated here); calls the panel's models concurrently (seven in the shipped config, config-driven — the mechanism calls whatever the config lists; the first call per slot is staggered by `(slot_index-1)×4s` with **1-based** slot indexing — `slot_index` is the model's 1-based position in the ordered `critic_slots` list — to avoid rate-limit bursts; stagger is a start-delay, not serialization, so the round still runs in parallel; the stagger applies to each model's **first** call only — retry attempts follow the backoff sleeps); per-model HTTP timeout default 600s, overridable per model via a `timeout` key in `providers.yaml`, so a slow model's effect on the round is bounded by its own budget rather than unbounded); applies the retry policy (unparseable → ≤1 retry, i.e. up to 2 attempts — the extractor's truncation repair is part of extraction, not a retry; transport/timeout/429 → ≤5 tries with adaptive backoff — 429 backoff 30s × attempt (attempt 1 → 30s, 2 → 60s, 3 → 90s, 4 → 120s; the ≤5 bound caps total backoff at 300s), other transport failures 8s × attempt (≤80s total); mixed failure codes sleep per-code on the shared attempt counter (a 429 then a 5xx = 30s then 16s); a timeout counts as a transport failure, against the ≤5 transport budget, not the invalid budget; any non-429 4xx — 400 bad request, 401/403 auth, 404 not found, 413 context-window overflow — is **deterministic client error**: not retried, it breaks that model's attempts immediately (429 is the only retryable 4xx); a **200 OK whose body is not valid JSON for the provider's response shape** is treated as a transport failure (retried per the budget); 5xx/timeout follow the ≤5 transport budget; a per-model `timeout` override changes only the per-call budget — the retry/backoff policy is unchanged; no cross-round exclusion — a failed critic participates again next round); enforces the response schema validity rule (unparseable, or `overall_score < 10` with zero issues → invalid — `overall_score` is the critic's holistic judgement, emitted by the critic; the script does not compute it from the dimension scores); validates each output against the same schema that `validate_critique.py` enforces (an embedded copy of the shape rules, kept in sync with that script); and writes one JSON per round under `--out` (default `outputs/critique-log/`) as `pass{1|2}-round{N}-{document}.json` — the JSON is written even when `n_valid == 0` (the round is logged; escalation is a printed note). `--round N` is a label for the output file and log lines (default 1, positive integer; `{document}` in the filename is the `--name` id, used **verbatim** — it must be a plain document id, no path separators, since it becomes part of the filename) — this script performs exactly one pass over exactly one document per invocation; a multi-round session is driven by repeated invocations from the agent, and the round cap bounds that session, not a single run (the script accepts `--round-cap` for contract parity with the sub-skill and validates it — positive integer or 0 — but the cap itself is enforced by the critique-loop sub-skill's stopping logic; with `--round-cap 0` the cap is disabled and the consecutive-non-progressing escalation remains the session's termination safeguard. A `--round` label beyond `--round-cap` is not validated — the cap is session-level and the script is one invocation; the sub-skill is responsible for not invoking past the cap). Document, config, and `--out` paths are resolved relative to the current working directory. The document is read as UTF-8 text (no length cap; a UTF-8 BOM, if present, is passed through as content — not stripped; a document that is not valid UTF-8 is a config error — exit 2; a document that exceeds a model's context window surfaces as a provider 4xx and is covered by the deterministic-client-error rule). The output directory is created if missing; the round JSON is written **atomically** (temp file `<filename>.tmp` in the same directory — same filesystem, so the rename is atomic — then `os.replace`), so an interrupted round leaves either the previous file or a complete new one, never a partial JSON. The whole panel is validated **before any model is called**: an entry naming an unknown provider, a slot model not present in its provider's `models`, a provider whose `key_env` key is unset **or empty** in the environment (checked once per distinct provider used by a slot), a `--name` containing path separators **or an empty `--name`**, a `providers.yaml` that does not parse, an **empty `critic_slots`**, or a per-model `timeout` that is not a positive number is a config error — exit `2` with a clear message; the script never burns a round discovering a typo'd provider or a missing key (a missing key would only produce a doomed 400), and never writes a malformed filename. Duplicate slot entries are **not** validated — a duplicated slot simply runs twice (config-author responsibility). `providers.yaml` is read fresh on every invocation — an edit between rounds takes effect on the next invocation (the script holds no cross-invocation config state). An unwritable output directory also exits `2` with a clear message rather than a traceback. Exit codes: `0` when the round completes with at least one valid critic; `3` when the round completes with `n_valid == 0` (no usable signal — the escalation note `escalation: round produced no valid critics` goes to stderr and the JSON is still written); `2` for any internal error (CLI parse error, missing/unreadable document, missing/unreadable/malformed `providers.yaml`, unknown provider, missing env key, bad `--name`, unwritable output — each with a clear message on stderr); no other codes are produced.

**Output JSON (top-level schema):** the file written per round has exactly `document` (the `--name` id), `pass` (1 or 2), `round` (the `--round` label), `critics` (an array containing **only the valid critiques**, ordered by 1-based slot position — deterministic, independent of completion order; failed/invalid critics appear in the stdout log only, never in the JSON), and `n_valid` (the `critics` array length — redundant by design: a convenience field mirroring `len(critics)`, part of the fixed schema). Timeout precedence: a per-model `timeout` key in `providers.yaml` overrides the global `--timeout` flag; the flag is the default for models without one.

**FR-2 — `kit/scripts/validate_critique.py`.** CLI: `--file <critique-log.json>`; when `--file` is omitted, reads the same JSON document from stdin. Reads a critique-log JSON and re-validates its **shape** against the PLAN.md §4.3 schema: the top-level envelope (`document` string, `pass` int, `round` int, `critics` list, `n_valid` int equal to `len(critics)`) and each critic's fields/types/presence, reporting any malformed entries — shape only, with **no enum constraints** (field values are not restricted to fixed sets). Semantic validity — unparseable, or `overall_score < 10` with zero issues — is the orchestrator's rule (FR-1), not this script's; this script checks shape only. Exit codes: `0` when the input is well-formed per the schema, `1` when any malformed entry is found (the offending field is named in the report) or when the input cannot be read/parsed (a clear message goes to stderr). Used by the loop and by verification tests.

**Required vs optional fields (schema):** required on each critic — `model`, `document`, `round`, `pass`, `overall_score`, `scores` (all five of `clarity`, `completeness`, `edge_case_coverage`, `internal_consistency`, `testability`), `issues` (array — **an omitted `issues` field is invalid**; an empty array is the only valid "no issues" form; each issue requires `section`, `category`, `problem`), `verdict`. Optional per issue — `why_it_matters`, `suggested_fix` (informational, not validated for content).

**FR-3 — `kit/skills/critique-loop/SKILL.md`.** The 11th sub-skill: instructs the agent how to invoke the orchestration script for a given document and pass, how to read the resulting JSON, how to triage issues (objective → resolve; needs_clarify → compile the list; false positive → reject with reason), and how to apply the stopping conditions. Marks the boundary between the human-guided adjudication (the agent) and the mechanical scoring (the script).

**FR-4 — Config-driven panel.** Neither script hard-codes a model list; both load `providers.yaml` (M1). `critic_slots` order is the critique order. Model additions are data-only (US-4).

## Edge Cases & Rules

- **A "round"** = one full concurrent call to the seven-model panel for a given document+pass invocation. A "session" = the agent's repeated invocation sequence for a document+pass (consecutive rounds across invocations, driven by the critique-loop sub-skill). A **"currently-valid critic"** = a critic whose critique passed the validity rule in that round (a member of that round's `critics` array). A round is **"progressing"** when the document changed in response to it or it surfaced at least one issue triaged as genuinely new and actionable; otherwise it is **non-progressing**; two such rounds back-to-back (no progressing round between them) are "consecutive".
- **Free-tier transport:** 429 → adaptive backoff (`30 × attempt` seconds) and retry; 5xx → backoff (`8 × attempt`); timeout → backoff (`8 × attempt`). Bounded to ≤5 transport tries per round. A critic that still fails is logged and absent for that round only — the round completes with the remaining valid critics, and the critic participates again next round.
- **Never exclude across rounds:** a critic that fails a round (invalid or transport) participates again next round — there is no session-level flag or exclusion. Never silently stops because scores aren't 10 (PLAN.md §4.3).
- **Input/errors:** if the document path is missing/unreadable/empty, or `providers.yaml` is missing/malformed, the script **HALTS** with a clear error — it never critiques nothing. A document that exceeds a model's context window surfaces as a provider 4xx (e.g. 413) and is covered by the deterministic-client-error rule.
- **All critics fail in a round:** if `n_valid == 0` for a round, the round produces no usable signal; the script records it (`n_valid: 0` in the JSON, exit 3, escalation note on stderr) — and this round **never** counts as advancement (the Pass-2 stopping condition is vacuous here and deliberately does not apply). The session-level logic (the critique-loop sub-skill) tracks consecutive non-progressing rounds and, on the **second consecutive** one, escalates to the human — the escalation is a message to the human in the session, never a silent loop — and the round cap bounds the session. There is no minimum quorum — a round completes with whatever valid critics it got; `n_valid == 0` is the only "no signal" case.
- **Round cap:** default 25 per pass, configurable (`--round-cap`, `0` disables); at the cap the loop exits and prints an escalation summary to the human — never exits without telling anyone (PLAN.md §4.4).
- **Unparseable response:** retried ≤1 time (≤2 invalid attempts total) after which it is invalid. Extra fields beyond the schema are ignored, not invalid. The extractor is deliberately tolerant: it accepts markdown-fenced JSON (fences anywhere in the response, not just at the start), surrounding prose — including prose that itself contains braces — trailing commas, and output-cap truncation (it best-effort closes an unterminated string and appends the minimal closing brackets, trying every `{` as a candidate JSON start **in text order — the first candidate that passes the full validity check wins**, so a bad repair never counts). Single-quoted JSON is not repaired.
- **Truncated response:** each provider call carries a generous output cap (NVIDIA NIM `max_tokens` 8000, Google `maxOutputTokens` 8000, Ollama `num_predict` 12000) because verbose critics routinely exceed small caps; a response still truncated by the cap is repaired best-effort by the extractor, and if the repair fails validation it is treated as invalid.
- **Empty issue list with score < 10:** invalid (noise), retried.
- **Concurrency:** the panel runs concurrently (all models at once, first call staggered to avoid rate-limit bursts); a slow model must not block the round past its timeout. Each attempt enforces a **hard wall-clock deadline** (socket timeouts alone do not bound free-tier calls that drip bytes slowly) — default 600s per call, overridable per model via a `timeout` key in `providers.yaml`; since calls overlap, the round's wall-clock is bounded by the slowest model's budget, not the sum — worst case per model ≈ 5 × per-call budget + backoff + stagger. On **any** final failure — invalid twice, or transport exhaustion — the script logs a short snippet of the critic's last raw response to its stdout log (the same stream as the per-model progress lines) — up to 300 code points (Python string indexing), whitespace-normalized (runs of whitespace collapsed to single spaces, trimmed), printed as `last raw text: <snippet>`; when no raw response exists (e.g. timeout before any bytes), the snippet is omitted — so the failure is diagnosable; the snippet is the critic's response text, which cannot contain keys (keys travel only in request headers/URLs, never in the prompt). Concurrent invocations writing the same output file (same doc+pass+round) race with last-writer-wins; no locking is performed (out of scope).
- **No secrets:** the three provider keys — `NVIDIA_NIM_API_KEY`, `GOOGLE_AISTUDIO_API_KEY`, `OLLAMA_API_KEY` — are read at runtime from the process environment via each provider's `key_env` field in `providers.yaml`; keys are never logged, embedded in prompts, or written to any file.

## Acceptance Criteria

**AC-1.** `kit/scripts/orchestrate_critique_loop.py`, `kit/scripts/validate_critique.py`, and `kit/skills/critique-loop/SKILL.md` exist and are **non-stub** — a stub is a file that is empty, a placeholder (`TODO`/`pass`/`NotImplemented` only), or a skeleton with no real implementation.

**AC-2.** Both scripts read the panel from `kit/config/providers.yaml` (no hard-coded model list); the ordered `critic_slots` drives critique order.

**AC-3.** The retry policy is implemented exactly per the edge cases: ≤1 retry on unparseable (≤2 invalid attempts), ≤5 tries with growing backoff on transport/429/5xx/timeout, no cross-round exclusion (a failed critic participates again next round), all-fail escalation, and a 25-per-pass round cap with escalation. Pass 2 advances (the agent proceeds to the next round, and eventually to the next document) only when every currently-valid critic scores perfect (or the round cap escalates) — a round with `n_valid == 0` **never** advances: the stopping condition applies only to rounds with at least one valid critic (the vacuous-truth case is the no-signal/escalation path, exit 3).

**AC-4.** Output JSON matches the PLAN.md §4.3 schema and is written to `outputs/critique-log/pass{1|2}-round{N}-{document}.json`; `validate_critique.py` re-validates it.

**AC-5.** The `critique-loop` sub-skill instructs the agent on invoking, triaging (objective/needs_clarify/false-positive), and stopping.

**AC-6.** No secrets introduced; the three provider keys read at runtime from the environment by their `key_env` names, never logged.
