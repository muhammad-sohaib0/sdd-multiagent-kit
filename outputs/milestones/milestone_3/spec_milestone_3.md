# SDD Multi-Agent Kit — Milestone 3 Spec

**Document:** `spec_milestone_3.md`
**Milestone:** 3 of 5
**Status:** Draft
> Companion to: `outputs/milestones/milestone_3/spec_milestone_3.md`

## Cumulative History

Inherited from M1 (kit content under `kit/`, providers.yaml, ten sub-skills) and M2 (critique engine under `kit/scripts/`, `critique-loop` sub-skill), all verified. This milestone ships the distribution/install layer that PLAN.md §1 promises: installable with a single `npm install`, free-tier only, auto-detecting target tools, installing into them directly with no manual configuration. Grounding: PLAN.md §10 (Setup Wizard Flow §10.1, Target Tools §10.2, Agent-Skills Standard §10.3, Extension Pattern §11.4) and §11.3 (repo structure: `bin/setup-wizard.js`, four `installers/*.js`, `package.json`).

## Goal

Deliver the npm installer: an interactive setup wizard (`bin/setup-wizard.js`) plus four tool adapters (`installers/{claude-code,claude-desktop,opencode,antigravity}.js`) that collect the three API keys once, detect which supported AI tools are installed, let the user choose which to install into, copy the kit's skill files to the correct location per tool (Agent-Skills standard, §10.3), and confirm the `/sdd` trigger is active. Adding a tool later means one new adapter file + one registration — no change inside `kit/` (the extension pattern, §11.4).

## User Scenarios

**US-1 — One-time setup.** A user runs `npm install -g sdd-multiagent-kit && sdd-setup`. The wizard asks for all three keys in one pass, detects installed tools, installs into the chosen ones, and confirms `/sdd` is live.

**US-2 — Pakistani-user NVIDIA gap.** A user is offered a "Guide for Pakistani users" **Learn more** option directly under the NVIDIA key prompt (for every user, not only those without a paid signup — the option's *content* is what targets the signup gap). The slot is reserved (§12); the guide's content is supplied separately by the maintainer.

**US-3 — Tool subset.** Only OpenCode is installed. The wizard detects just it, installs into it, and skips the others. Nothing breaks if a tool is absent.

**US-4 — Add a tool later.** The four adapters (`installers/{claude-code,claude-desktop,opencode,antigravity}.js`) ship in this milestone. A contributor adds a *future* tool by writing one file implementing `detect()/install()/confirmEnabled()` and registering it. The kit content is untouched.

## Functional Requirements

**FR-1 — `bin/setup-wizard.js`.** Interactive Node CLI (prompts read via stdin) that: (1) collects all three API keys in one setup pass, in this order: `NVIDIA_NIM_API_KEY`, `GOOGLE_AISTUDIO_API_KEY`, `OLLAMA_API_KEY` (the env-var names, matching `providers.yaml`); (2) directly beneath the NVIDIA key prompt (immediately after the NVIDIA key is entered, before the next key prompt), offers a "Guide for Pakistani users" **Learn more** option — a y/N prompt offered **every interactive run** (regardless of whether the key is already set in env; on non-TTY stdin it is skipped with the key prompts — see key handling); answering `y` prints the link as a plain-text line to the reserved guide's docs location (a wizard constant `GUIDE_SLOT` = `docs/GUIDE.md`'s `#guide-for-pakistani-users` section — the target file ships in M4; in this milestone the link names the reserved location; slot only — content supplied separately, never fabricated); input parsing is `y`/`Y` (case-insensitive prefix `y`) = yes, and anything else including empty input = no (default-No); (3) runs each adapter's `detect()` to find installed tools; (4) lets the user pick which detected tools to install into; (5) runs each chosen adapter's `install(kitPath)` to copy the kit files to the tool's location; (6) runs `confirmEnabled()` and prints a success/trigger message for each. The key step is **onboarding only**: keys are held in memory for the session and are never written to disk, echoed back, transmitted, or used by the wizard — the kit reads them from the process environment at runtime (the user sets them in their own environment, e.g. a shell profile or `.env`), and any keys entered into the wizard are discarded on process exit. Key-entry input rules: an entry that is empty, or whitespace-only after trimming, counts as a **skip**; an entry that is non-empty after trimming but contains **internal whitespace** (any Unicode whitespace, including tabs) or control characters is rejected with a message and re-prompted (a format sanity check — the wizard performs no provider validation); ordinary key punctuation — hyphens, underscores, dots — and non-ASCII characters are accepted. "Opaque strings" means the wizard and kit never parse or interpret key content (no structure assumed); the whitespace/control rejection is the single exception — a hygiene guard, because whitespace in a key would break the shell-profile/`.env` export the user is told to write (a key is expected to be a single unbroken token). The re-prompt loop has no fixed retry count (it repeats until a valid entry or a skip) and Ctrl-C/EOF aborts at any point. After the session the wizard prints a final reminder (both TTY and non-TTY runs) listing all three names in the fixed order (NVIDIA, Google, Ollama), each with its status — `NVIDIA_NIM_API_KEY (set in env)` when `process.env` already has it, `NVIDIA_NIM_API_KEY (not set — add it to your shell profile or .env)` otherwise — and marks the ones the user skipped this run. Keys entered during this run are held in memory and discarded on exit, so they are **not** reported as "set in env"; a key entered this session is reported as `entered this session (not persisted) — add it to your shell profile or .env`. Skipped keys never affect the exit code (exit codes reflect install/confirm outcomes only), and there is no back-navigation — skipping is final for the run. On a non-TTY stdin the key prompts **and** the Pakistani-guide prompt are skipped (all key-step prompts are TTY-only), and the reminder is printed instead. Key prompts require a TTY (masked entry, no echo, so keys never appear in scrollback or logs); on a non-TTY stdin the key prompts are skipped with the reminder printed instead — the wizard never echoes a key in cleartext.

**FR-2 — Adapter interface (extension pattern, §11.4).** Every file in `installers/` implements:
- `name` — a display name string (e.g. `Claude Code`); this is the tool's identifier everywhere in the wizard UI (the detected list, the selection prompt, and per-tool output).
- `detect()` — returns `{ installed: bool, location: string|null }`, where `installed` means the *tool* is present (its config directory and/or executable — no network), not that the kit is already installed in it, and `location` is the absolute path of the folder where the kit is **already installed** for that tool. The two fields are **independent**: `location` reflects the kit-folder state on disk (non-null exactly when the kit folder is populated) and is decoupled from `installed` — e.g. OpenCode installed at `~/.opencode/` but its shared `.claude/skills/sdd-multiagent-kit/` folder empty or absent → `installed: true, location: null`; a populated kit folder with the tool absent (orphaned install) → `installed: false, location: <path>`. Detection is determined by filesystem checks only. Any filesystem error during detection (EACCES, ENOTDIR, ELOOP, EMFILE) is caught, logged as a warning, and treated as `installed: false` — detection never aborts the wizard.
- `install(kitPath)` — copies the entire `kit/` directory tree into the tool's location per §10.3, creating the config directory if absent, and returns the absolute destination path of the installed skill folder (the existing path when the OpenCode no-op case applies). The "copies only if …" preconditions in FR-3 (OpenCode's no-op, Claude Desktop's copy-if-not-populated) are **guards on when `install()` performs the copy**; when a guard does not trigger, the copy operation itself is always this whole-tree write. Errors (permission errors, a target path existing as a file rather than a directory, an unwritable or uncreatable home/destination directory, etc.) throw an `Error` whose message is one line; the wizard prints the message verbatim per-tool (any thrown value is handled — a non-`Error` throw is stringified), reports that tool as failed, and continues with the others (a failed tool contributes to exit 1 — it never aborts the run). Adapters are expected to prefix their error message with the tool id (e.g. `claude-code: permission denied <path>`) as a readability convention — the wizard does not verify or enforce the prefix.
- `confirmEnabled()` — takes no arguments (it re-checks the filesystem at the tool's own location internally) and returns `{ installed: bool, location: string|null }` (same shape as `detect()`); the wizard calls it **only after a successful `install()`**, so `location` is populated by then, and the trigger is confirmed exactly when `installed` is `true` (the wizard prints a success/trigger message then, and "not confirmed" otherwise). For the three native tools it verifies the copied `SKILL.md` carries `name: sdd-multiagent-kit` in its YAML frontmatter (the frontmatter is the `---`-delimited block at the top of the kit's `SKILL.md`; the native slash command derives from that skill name, so this file check is the registration check). For Antigravity it verifies the copied `SKILL.md` description contains the canonical invocation phrase `Invocation: /sdd`, which the adapter re-asserts idempotently on every install: it replaces any existing line beginning `Invocation:` in the description with the canonical `Invocation: /sdd` line, or appends the canonical line beneath the `version:` frontmatter key when none exists (so re-runs converge to it — this injection is adapter-owned content layered on the kit-owned copy, not part of the shipped `kit/` tree). The check is case-sensitive on the exact phrase the adapter writes (matching its own output is deterministic).

`kitPath` = a single absolute filesystem path to the `kit/` directory whose content is copied (a single path — the parameter is not a list or source→dest mapping). The wizard derives it by walking parent directories from its own location until it finds a `package.json` carrying `name: sdd-multiagent-kit` **whose sibling `kit/` directory actually exists and contains `SKILL.md`** (both conditions must hold — the extra `kit/`/`SKILL.md` check keeps monorepos and workspace installs from matching a package root that is not this kit); the nearest matching ancestor wins — if the walk reaches the filesystem root without a match, the wizard errors (exit 2). The wizard discovers adapters by requiring each `.js` file directly under `installers/` (non-recursive; non-`.js` files are ignored — they may ship for other purposes, e.g. a per-tool README, without conflict). If `installers/` is missing or contains no `.js` files, the wizard errors at startup (exit 2) with a clear message. Each discovered file must export `name`, `detect`, `install`, and `confirmEnabled` (CommonJS `module.exports`, matching Node ≥18 and the stdlib-only constraint), or the wizard errors at startup (exit 2) with a clear message — never silently ignored; a file that **throws during `require()`** (syntax error, missing module) is likewise reported and exits 2; two discovered adapters exporting the same `name` is also a configuration error (exit 2, listing both files; the name comparison is case-sensitive exact match — discovery order is irrelevant because of the uniqueness requirement, so the wizard's `readdirSync` order is fine). A tool's *registration* is therefore its file itself — adding a tool means dropping one new file into `installers/`; there is no central registry to edit. Install paths are resolved at runtime via `os.homedir()` (the `~`/`%USERPROFILE%` distinction is the runtime's business, not the spec's); if `os.homedir()` fails or resolves empty, the wizard errors clearly and exits 2 before any install.

**FR-3 — Per-tool install locations (§10.3).**
- Claude Code: `~/.claude/skills/sdd-multiagent-kit/` (user-level; project-scoped `.claude/skills/` is out of scope) → native `/sdd` slash command derived from the folder name (the tools register a native slash command from the skill folder name, per §10.3).
- Claude Desktop: same user-level location as Claude Code (per §10.3 it shares Claude Code's configuration) → automatic. Its `detect()` verifies Claude Desktop itself — its app config directory (presence of that directory is the signal; it need not be non-empty — the dir's existence marks the app installed) — not just Claude Code's presence, with per-platform paths: macOS `~/Library/Application Support/Claude`, Windows `%APPDATA%\Claude`, Linux `~/.config/Claude`; `location` is the shared folder when populated, else `null`; its `install()` copies only if the shared folder is not populated with the kit. Claude Code and Claude Desktop share one destination folder: installing both is idempotent (the second `install()` re-copies the same content into the same folder — no conflict; the wizard treats them as two independent selections).
- OpenCode: reads `.claude/skills/` directly — so it shares the Claude Code user-level location and needs **no separate copy** when the kit is already present. The OpenCode adapter's `detect()` checks for OpenCode itself: installed when a non-empty OpenCode config directory exists at `~/.opencode/` or `~/.config/opencode/` (these two are the supported locations; on Linux the `$XDG_CONFIG_HOME/opencode` path is also accepted when `XDG_CONFIG_HOME` is set) **or** the `opencode` executable resolves on PATH (either signal alone suffices — no network). PATH scanning is done with the Node stdlib `fs` only (checking each entry of `process.env.PATH` for an `opencode` file — on Windows also matching `opencode.exe`/`opencode.cmd`/`opencode.bat`; matching is case-sensitive on the exact basename; an unset or empty PATH simply yields no PATH signal, and registry-resolved Windows PATH entries are out of scope); the wizard never shells out to `which`/`where`. `location` is the shared `.claude/skills/sdd-multiagent-kit/` path when populated, else `null`. "Populated" = the folder exists and is non-empty (contains at least one entry, in practice `SKILL.md`). Note the two uses of "populated" deliberately differ: `detect()`'s `location` uses the loose sense (any non-empty folder — a kit-presence *signal*), while `install()`'s no-op uses the strict sense (the folder is kit-marked — a kit-*identity* check). Its `install()` is a no-op **only when the shared folder is populated with the kit** (its `SKILL.md` carries `name: sdd-multiagent-kit`); otherwise — folder absent, partially populated, or holding stale/non-kit content — it performs a real copy, refreshing the shared folder. OpenCode's `install()` is the one deliberate exception to the in-place re-run rule (§"Re-runs"): it never overwrites kit content that is already current — an OpenCode-only re-run intentionally does not refresh an existing kit-marked copy (refresh via a Claude Code/Desktop install, or remove the shared folder first).
- Antigravity: `.agents/skills/sdd-multiagent-kit/` → separate copy required. Its `detect()` considers the tool installed when the agent config directory `~/.agents/skills/` exists (that directory is the detection signal — no bundle-id or app probing in this milestone); `location` is `~/.agents/skills/sdd-multiagent-kit/` when populated, else `null`. `confirmEnabled()` checks the copied SKILL.md description carries the invocation phrase (no native slash registry exists in this tool).

**FR-4 — `/sdd` trigger.** The kit's folder name (`sdd-multiagent-kit`) yields `/sdd` for the three tools with a native slash-command registry; for Antigravity the trigger is embedded in the SKILL.md description as the literal line `Invocation: /sdd` so explicit invocation is recognized. The wizard confirms the trigger for each installed tool.

**FR-5 — `package.json`.** Declares the package (`name: sdd-multiagent-kit`, a semver `version`, `bin: { "sdd-setup": "bin/setup-wizard.js" }`, `engines: { "node": ">=18" }`), MIT license (per §12 open decisions), and no dependencies — neither runtime nor development (the wizard uses only the Node stdlib — `readline`/`fs`, plus raw-mode stdin for masked key entry — and there is no build step). **`package.json` is the version's single source of truth:** the wizard reads it at runtime for `--version` and the `--help` banner rather than carrying a copy, and the twelve `SKILL.md` frontmatter `version:` keys (master + eleven sub-skills) must agree with it, since all thirteen files ship in one tarball. `scripts/bump-version.js` sets them together and `--check` asserts the agreement; this milestone's tests assert the *agreement*, never a literal version, because pinning one makes a correct release bump fail the suite (see ADR-005). A version the wizard cannot determine is an error (exit 2), never a fabricated number. `files` is the exhaustive package-content list: `kit/`, `bin/`, and `installers/` (the wizard and the adapters it requires must ship), `docs/` (the wizard's reserved-guide pointer and the README's guide link both resolve into it, so omitting it ships two dangling references), plus `LICENSE`, `README.md`, and `CHANGELOG.md` (npm always includes `package.json` and the `README` regardless of the list; the list governs the rest). The list also carries the negated entries `!kit/**/__pycache__` and `!**/*.pyc`: the critique engine under `kit/scripts/` is imported by the verification suites, which leaves interpreter-version-specific bytecode beside it, and a directory allowlist would otherwise sweep it into the tarball. The exclusion must live inside `files` — a `.npmignore` cannot override an allowlist. Repo-only tooling stays out of the tarball by omission: `scripts/` and `.github/` are absent from `files` and asserted absent from the packed contents. The list *ships* `LICENSE`/`README.md`/`CHANGELOG.md`/`docs/` when they exist; authoring their full content is deferred to M4 (§ Out of Scope) — this milestone declares the package shape (license: MIT per §12) without fabricating repo documentation. `engines` is advisory but the wizard checks `process.version` at startup and errors (exit 2) on Node below 18. `bin/setup-wizard.js` carries the `#!/usr/bin/env node` shebang and the executable bit, so `npm install -g` exposes `sdd-setup` directly.

## Edge Cases & Rules

- **No secret values in the repo or committed files.** Keys are stored only in the user's own environment/tool config; the wizard never writes a key into `kit/`, the repo, or a PHR/log (PHR = Prompts-History-Record, the narrative log under `outputs/history/prompts/` per §4.4).
- **Tool not installed:** `detect()` returns `installed: false` → the wizard skips it; absence of a tool is never an error.
- **Install failure:** an adapter's `install()` throws → the wizard reports which tool failed and continues with the others (never aborts the whole run silently).
- **`confirmEnabled()` failure:** reported per-tool; the wizard marks that tool as "not confirmed" and continues.
- **Config directory absent:** `install()` creates the target directory before copying.
- **Antigravity has no native slash registry:** the trigger is embedded in the description; `confirmEnabled()` checks the phrase is present (never assumed to work like the others).
- **Pakistani-guide slot:** a **Learn more** option directly beneath the NVIDIA key prompt that prints a link to the reserved guide location in the docs; the wizard does not fabricate the guide's content.
- **Re-runs:** re-running setup overwrites the kit files in place — the adapter copies the whole shipped `kit/` tree, writing each source file into the destination at its relative path (creating or overwriting files of the same name); it never deletes other files in the destination folder — and re-confirms the trigger; idempotent for the kit content. **OpenCode is the one deliberate exception:** its `install()` no-ops when the shared folder is already populated with the kit (FR-3) — it never overwrites kit content that is already current; all other adapters overwrite in place on every run. Adapter-owned additions (the Antigravity `Invocation: /sdd` line) are layered on top and re-asserted idempotently. There is no version check — a re-run is a plain re-install, and the wizard re-prompts for the tool selection each run. A Ctrl-C during `install()` may leave a partial destination folder; a re-run's copy overwrites it, so the re-install heals partial state (the OpenCode no-op only fires when `SKILL.md` is present and kit-marked, so a partial OpenCode copy without that marker is re-copied on the next OpenCode install too).
- **Keys provided again:** the wizard asks for all three each run (it does not auto-load prior keys); before each key prompt it checks `process.env` for a prior value and prints a hint (e.g., `(existing value found)`) if one exists — an empty-string env value counts as no value; the user may **skip** a key (leave it empty) to keep that existing env value — if no env value exists either, skipping warns and continues without that key (tools needing it fail at runtime, which is why the kit's retry machinery exists). The wizard never blocks on a skipped key, and skipping never affects the exit code. Key entry is **masked** (no echo, stdlib raw-mode input) so keys never appear in terminal scrollback; key prompts require a TTY — on a non-TTY stdin they are skipped with the reminder printed instead, and the wizard never echoes a key in cleartext.
- **Ctrl-C / interrupt:** the wizard aborts cleanly without writing partial config (nothing is persisted until a tool's `install()` runs) and exits 130 (the SIGINT convention). Ctrl-C during an `install()` may leave a partial destination folder; a re-run's copy overwrites it, so the re-install heals partial state (idempotent).
- **EOF on stdin:** EOF with no pending input (e.g. a closed pipe) is treated as a user abort — exit 130; EOF after a complete selection proceeds normally.
- **Invalid tool selection:** the wizard re-prompts until the user enters a valid tool name, `all`, or aborts (Ctrl-C); empty input re-prompts too. The valid names are the adapters' exported `name` values (the display names on the "Detected tools" line), accepted case-insensitively, comma-separated; there is no "none" option — the user cannot deselect everything; zero installed tools occurs only when nothing was detected (exit 0) or on abort (130). On a non-TTY stdin the selection prompt reads lines via readline (the raw-mode masked reader is TTY-only); piped input (e.g. `echo all | sdd-setup`) works for selection.
- **Nothing selected:** if no tools are detected, the wizard reports completion without writing anything and exits 0.
- **Kit source missing:** if the kit source directory (`kitPath`) is absent or unreadable, the wizard errors with a clear message before any prompt and exits 2 (configuration error).
- **Exit codes:** `0` = all chosen tools installed and confirmed (including the nothing-selected case); `1` = completed but one or more tools failed/not confirmed (partial success); `2` = configuration/usage error before any install (bad arguments, missing kit source, Node <18, unresolvable home directory); `130` = aborted by the user (Ctrl-C or EOF). No env-var overrides exist — `--help`/`-h` prints usage and exits 0, `--version` prints the package version and exits 0, any other argument exits 2.

## Out of Scope (deferred)

- Repo docs, LICENSE, README, CHANGELOG, CONTRIBUTING, `docs/` — **M4**.
- Examples / sample-project — **M5**.
- The kit content itself and the critique engine (already M1/M2) — the installer only copies/installs them.
- Actual content of the "Guide for Pakistani users" — a reserved slot only (PLAN.md §12).
- A non-interactive/CI mode and an uninstall command — future, not this milestone.
- Concurrent `sdd-setup` runs — the wizard is interactive and single-user (one terminal); a second run from another terminal is not coordinated and could race on a shared install folder. Documented limitation, not handled this milestone.

## Acceptance Criteria

**AC-1.** `bin/setup-wizard.js` and the four `installers/*.js` exist and are **non-stub** (a stub = empty, placeholder, or `TODO`-only with no real implementation), and each adapter exports `detect()`/`install(kitPath)`/`confirmEnabled()` as functions with the FR-2 signatures and return shapes.

**AC-2.** The wizard collects all three keys in one pass and offers the Pakistani-guide slot directly beneath the NVIDIA key prompt (slot only).

**AC-3.** Detection skips absent tools gracefully; install failure is reported per-tool and the run continues.

**AC-4.** Install locations and the trigger handling match §10.3 exactly for all four tools (Antigravity uses the description-embedded trigger).

**AC-5.** `package.json` is valid (`bin` points to `setup-wizard.js`, no runtime deps, MIT license), and installing the kit content never writes a secret value into the repo or a log.

**AC-6.** `sdd-setup` is runnable (the bin entry resolves and the wizard starts).
